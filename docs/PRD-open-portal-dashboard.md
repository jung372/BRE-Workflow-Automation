# PRD — 정보공개 청구 대시보드 추가

- 작성일: 2026-08-06
- 대상 저장소: `jung372/BRE-Workflow-Automation2`
- 선행 문서: [PRD-auto-deploy.md](PRD-auto-deploy.md)

## 1. 배경 및 목표

풍력 사업은 인허가 과정에서 여러 지자체·중앙부처 부서가 공문을 주고받는다. 이 공문들은 정보공개포털(open.go.kr)의 **정보목록**에 공개되지만, 담당자가 직접 검색해야만 확인할 수 있다. 사업명으로 새 공문이 올라왔는지 자동으로 감시하면 인허가 진행 상황을 선제적으로 파악할 수 있다.

**목표.** 사전 지정한 사업명 키워드로 open.go.kr을 시간당 조회해 신규 공문을 감지하고, 기존 대시보드에 **"정보공개 청구"** 카드로 표시한다. 각 항목은 **제목 / 발송처(말단 부서명) / 날짜**를 보여준다.

**부가 목표.** 키워드를 코드에 하드코딩하지 않고 웹에서 수정 가능하게 한다. 이 문서의 6항에서 실현 가능성을 검토한다.

## 2. 사전 조사 결과 (실측)

추측을 배제하기 위해 실제로 open.go.kr을 호출해 구조를 확인했다. 아래는 모두 **2026-08-06 실측값**이다.

### 2.1 검색 결과는 정적 HTML이 아니다

`uniSrhMoreList.do`는 껍데기 페이지이며 `table`·`tbody tr`이 0개다. 결과는 JS가 AJAX로 받아 렌더링한다. **따라서 기존 `fetch_general`(테이블 파서)은 사용할 수 없다.**

### 2.2 실제 데이터 엔드포인트 — JSON API

| 항목 | 값 |
|---|---|
| URL | `POST https://www.open.go.kr/othicInfo/infoList/infoList.ajax` |
| 응답 | JSON (`Content-Type: text/html`이지만 본문은 JSON) |
| 구조 | `result.rtnTotal` (전체 건수), `result.rtnList[]` (레코드 배열) |
| 검색어 파라미터 | **`kwd`** |
| 기간 | `startDate` / `endDate` (`YYYYMMDD`). 미지정 시 최근 2개월로 강제됨 |
| 페이지 크기 | `rowPage` = 100 이면 100건까지 한 번에 반환 |
| 정렬 | 기본이 이미 최신순(`R_DATE` 내림차순) |

HTML 파싱이 필요 없다. 이는 `scrapers/eiass.py`가 POST API를 직접 호출하는 방식과 같은 부류다.

### 2.3 컬렉션 선택 — 정보목록이 정답

통합검색 아래에 형제 엔드포인트가 3개 있다. 사용자 지정 키워드로 각각 조회한 결과:

| 키워드 | 원문정보<br>`orginlInfoList.ajax` | **정보목록**<br>**`infoList.ajax`** | 결재문서<br>`mnstrSanDocList.ajax` |
|---|---|---|---|
| 시루풍력 | 0 | **39** | 0 |
| 왕신풍력 | 0 | **63** | 0 |
| 해파랑육상풍력 | 0 | **61** | 0 |

> **핵심.** 원문정보로 조회하면 **전부 0건**이다. 반드시 **정보목록(`infoList.ajax`)** 을 써야 한다. 결재문서는 이 용도에 무의미하므로 제외한다.

### 2.4 세션 요구사항 — Playwright 필요

`정보목록`·`원문정보`는 JS가 심는 쿠키(`ufp` = fingerprint, `XSRF-TOKEN`)가 없으면 `rtnList`를 반환하지 않는다. `requests` 세션만으로는 실패한다.

검증된 절차:

1. Playwright로 `uniSrhMoreList.do?kwd=<임의>` 를 로드 → `setFingerPrint.ajax`가 자동 실행되어 쿠키 확보
2. 같은 브라우저 컨텍스트의 `context.request.post()` 로 AJAX 호출 (쿠키 공유)
3. 헤더에 `X-Requested-With: XMLHttpRequest`, `X-XSRF-TOKEN: <쿠키값>`, `Referer` 지정

`kepco.py`가 이미 Playwright 컨텍스트를 쓰므로 새로운 패턴이 아니다.

### 2.5 필드 매핑 — 요구사항과 정확히 일치

실측 레코드 예시:

```
INFO_SJ            : 전기사업 허가 신청에 따른 회신(경주시루풍력 2호)
NFLST_CHRG_DEPT_NM : 경상북도 경주시 도시개발국 도시계획과
CHRG_DEPT_NM       : 도시계획과
ALL_PROC_INSTT_NM  : 경상북도 경주시
R_DATE             : 20260804      P_DATE : 20260803
DOC_NO             : 도시계획과-13792
PRDCTN_INSTT_REGIST_NO : DCT1B2D6C2EA3A14C62BCFE3A87A4868CBB
```

| 요구사항 | 필드 | 비고 |
|---|---|---|
| 게시글 제목 | `INFO_SJ` | |
| **발송처 (마지막 부서명만)** | **`CHRG_DEPT_NM`** | **문자열 자르기 불필요 — 이미 말단 부서명이다** |
| 발송처 전체 계층 | `NFLST_CHRG_DEPT_NM` | 함께 저장해 상세 표시·검증용으로 쓴다 |
| 날짜 | `R_DATE` (등록일) | `P_DATE`(생산일)도 함께 저장 |
| 고유 식별자 | `PRDCTN_INSTT_REGIST_NO` | 신규 판정 키로 사용 |

> **차이점 하나.** 요청 시 예시로 주신 `경상북도>경주시>도시개발국>도시계획과`의 `>` 구분자는 화면 표시용이며, API는 **공백 구분**으로 반환한다. 어차피 `CHRG_DEPT_NM`에 말단 부서명이 따로 있으므로 파싱이 필요 없다.
>
> 다만 기관 자체가 발송처인 경우(예: `한국에너지공단`)에는 `CHRG_DEPT_NM`과 `NFLST_CHRG_DEPT_NM`이 동일하다. 표시 규칙은 "`CHRG_DEPT_NM`이 있으면 그것, 없으면 `NFLST_CHRG_DEPT_NM`의 마지막 토큰"으로 정한다.

### 2.6 키워드 정밀도 — 사업 전체명을 써야 한다

부분 키워드는 무관한 결과가 폭증한다.

| 키워드 | 정보목록 건수 | 판정 |
|---|---|---|
| 시루풍력 | 39 | 적정 |
| 시루 | 18,928 | 사용 불가 (시흥 지역화폐 "시루", 단양 "시루섬" 등) |
| 왕신풍력 | 63 | 적정 |
| 왕신 | 10,859 | 사용 불가 (왕신지구 수리시설, 강동 왕신리 등) |
| 해파랑육상풍력 | 61 | 적정 |
| 해파랑 | 1,850 | 사용 불가 (해파랑길 관광, "해파필터" 오탐) |

**지정하신 세 키워드가 모두 적정 수준입니다.** 키워드 편집 UI에는 이 특성을 안내하고, 결과 건수가 임계값(예 500건)을 넘으면 경고를 남긴다.

### 2.7 확인된 제약 — 페이징이 동작하지 않는다

`pageIndex`를 1→2로 바꿔도 **동일한 레코드가 반환**된다 (10건 중 10건 중복). 올바른 페이징 파라미터를 찾지 못했다.

**대응.** `rowPage=100`으로 전량을 한 번에 받고, `rtnTotal > 반환건수`이면 **경고 로그를 남긴다**(조용히 누락되지 않게). 실측 최대치가 8년치 63건이므로 100은 충분한 여유다. 초과 사례가 발생하면 그때 페이징 파라미터를 재조사한다.

## 3. 목표 / 비목표

**목표**

- G1. 지정 키워드로 open.go.kr 정보목록을 시간당 조회한다.
- G2. 제목·발송처(말단)·날짜를 추출해 상태 DB에 축적한다.

- G5. 기존 5개 사이트 모니터링과 Teams 보고에 영향을 주지 않는다.

**비목표**

## 4. 아키텍처 통합

기존 `SITES`는 "URL 1개 = 카드 1개" 구조다. 정보공개 청구는 **키워드 N개를 조회해 카드 1개로 집계**하므로 새 타입을 추가한다.

```
config.py
  SITES 에 항목 추가
    {"id": "open_portal", "name": "정보공개 청구", "icon": "📄",
     "color": "#a855f7", "type": "openportal",
     "url": "https://www.open.go.kr/com/search/uniSrhMoreList.do",
     "proxy": True}

scrapers/__init__.py
  type == "openportal" -> fetch_open_portal(site, p_instance)

scrapers/open_portal.py   (신규)
  1. 키워드 목록 로드
  2. Playwright 컨텍스트로 셸 페이지 1회 방문 -> 쿠키 확보
  3. 키워드마다 infoList.ajax POST (rowPage=100)
  4. 레코드 정규화 -> 키워드 간 uid 중복 제거 -> 날짜 내림차순
```

수집 결과는 기존 파이프라인을 그대로 탄다. `logic/runner.py`가 `state.py`로 신규를 판정하고 `data/status.json`에 기록하며, `push_to_github.py`가 발행하고, `notify_teams.py`가 Teams 보고에 포함한다. **런너·발행·배포 로직은 변경하지 않는다.**

### 4.1 조회 기간

`startDate = 오늘 - 90일`, `endDate = 오늘 + 1일`. 90일 고정 창이면 일별 결과 집합이 안정적이어서 `state.py`의 5일 전 기준 비교가 정상 동작한다.

### 4.2 신규 판정 키 — `state.py` 소폭 수정

현재 `item_id()`는 `제목||날짜||완료일||상태`로 ID를 만든다. open.go.kr은 `PRDCTN_INSTT_REGIST_NO`라는 진짜 고유키가 있으므로 이를 우선 사용한다.

```python
def item_id(n: dict) -> str:
    if n.get("uid"):        # open.go.kr 등 고유키가 있는 소스
        return n["uid"]
    ...  # 기존 로직 유지
```

기존 항목에는 `uid`가 없으므로 **하위 호환된다.** 기존 5개 사이트의 판정 결과는 바뀌지 않는다.

`update_site_state()`의 시간별 스냅샷 항목에 `dept`와 `keyword`를 추가한다(Teams 카드에서 발송처를 보여주기 위함). 기존 항목은 해당 키가 없으므로 `.get()`으로 안전하게 읽는다.

### 4.3 표시 계층

`app.js`는 `data.sites`를 순회해 카드를 자동 생성하므로 **카드 추가를 위한 HTML 수정은 필요 없다.** 상세 UI 설계는 5항에서 다룬다.

| 파일 | 변경 |
|---|---|
| `assets/app.js` | 키워드 칩 영역 + 항목별 키워드 배지 |
| `assets/styles.css` | 칩·배지 스타일, 카드 상단 그라데이션, 정렬 순서 |
| `presentation/teams_card.py` | `SITE_DISPLAY`에 `"open_portal": "정보공개 청구"` 추가 |

### 5.1 대시보드 UI — 키워드 칩 + 접기/펼치기

카드 헤더 제목 아래에 키워드를 배지 칩으로 표시한다. 기본은 접힌 상태이고, 넘치는 개수는 `+N ▾` 버튼으로 접어 둔다.

```
【접힌 상태】                        【펼친 상태】
┌────────────────────────────┐      ┌────────────────────────────┐
│ 📄  정보공개 청구           │      │ 📄  정보공개 청구           │
│    〔시루풍력〕〔왕신풍력〕 +1 ▾ │      │    〔시루풍력〕〔왕신풍력〕      │
├────────────────────────────┤      │    〔해파랑육상풍력〕       ▴ │
│ 신규 등록 게시글            │      ├────────────────────────────┤
│ 2                          │      │ 신규 등록 게시글            │
├────────────────────────────┤      │ 2                          │
│ ● 전기사업 허가 신청에 따른 │      └────────────────────────────┘
│   회신(경주시루풍력 2호)    │
│   도시계획과 · 08-04 〔시루풍력〕│  ← 항목별 매칭 키워드
└────────────────────────────┘
```

**항목별 키워드 배지는 별개 요소다.** 헤더 칩은 "무엇을 감시 중인가", 항목 배지는 "이 공문이 어느 사업 건인가"를 알려준다. 여러 사업의 공문이 섞여 나오므로 후자가 실사용에서 더 중요하다. 배지는 기존 날짜와 **같은 줄**에 배치해 높이 증가가 없다.

#### 구현 시 반드시 처리할 두 가지

`assets/app.js`의 `render()`는 카드가 이미 있으면 헤더를 다시 만들지 않고 본문만 갱신한다. 그리고 대시보드는 `AUTO_REFRESH_SEC = 300`으로 5분마다 자동 갱신된다. 여기서 두 가지 문제가 생긴다.

1. **펼침 상태가 초기화되면 안 된다.** 갱신마다 접히면 쓸 수 없다. → 상태를 `localStorage`(키: `kwExpanded:open_portal`)에 저장하고 렌더 시 복원한다.
2. **키워드를 바꿨는데 칩이 그대로면 안 된다.** 헤더가 1회만 생성되므로 키워드 편집이 전체 새로고침 전까지 반영되지 않는다. → 칩 영역을 전용 요소(`#kw-open_portal`)로 분리해 **매 렌더마다 다시 그리고**, 펼침 상태는 위 저장값으로 복원한다.

두 요구를 동시에 만족시키는 방법은 "칩 영역만 매번 재생성 + 상태는 외부에 보관"이다.

#### 표시 규칙

| 항목 | 규칙 |
|---|---|
| 접힌 상태 | 한 줄에 들어가는 만큼만 표시, 나머지는 `+N ▾` |
| 펼친 상태 | 전체 칩을 줄바꿈해 표시, `▴`로 접기 |
| 토글 요소 | `<button aria-expanded>` 사용 (키보드·스크린리더 대응) |
| `keywords` 없음 | 칩 영역 자체를 렌더하지 않음 (기존 5개 사이트 카드는 영향 없음) |
| 카드 색상 | `.card[data-id="open_portal"]::before` 그라데이션 추가 (미지정 시 기본 초록으로 표시됨) |
| 카드 순서 | `styles.css`의 `order` 규칙에 추가 (미지정 시 `order: 99`로 맨 뒤) |

### 5.2 저장하지 않는 필드 — 개인정보

응답에는 **`CHARGER_NM`(담당자 실명)** 이 포함된다. 대시보드는 GitHub Pages로 **공개**되므로 이 필드는 저장·표시하지 않는다. `FILE_NM`(첨부파일명)도 요구사항에 없고 개인정보가 섞일 수 있어 제외한다.

## 6. 키워드 편집 기능 — 실현 가능성 검토

요청하신 "웹사이트에서 키워드를 수정하는 기능"의 핵심 제약은 **대시보드가 GitHub Pages 정적 호스팅**이라는 점이다. 서버 코드가 없어 브라우저에서 보낸 수정 요청을 받을 주체가 없다.

### 6.1 검토한 4가지 방안

| 방안 | 방식 | 구현 비용 | 판정 |
|---|---|---|---|
| **A. 저장소 파일 직접 편집** | `config/keywords.json`을 GitHub 웹 편집기로 수정. 대시보드에 편집 화면 링크 버튼 배치 | 낮음 | **권장 (1단계)** |
| B. GitHub Issue 기반 | 이슈 본문에 키워드를 적고, 워크플로가 파싱해 파일로 커밋 | 중간 | 보류 |
| C. 사설 관리 페이지 | 서버 PC에 Flask 관리 화면을 만들고 Tailscale Serve로 노출 | 높음 | 선택 (2단계) |
| D. Pages에서 GitHub API 직접 호출 | 브라우저 JS가 토큰으로 파일 커밋 | 낮음 | **채택 불가** |

**D를 배제하는 이유.** 공개 정적 사이트의 JS에 넣은 토큰은 누구나 볼 수 있다. 저장소 쓰기 권한이 그대로 노출되므로 보안상 성립하지 않는다. OAuth 앱으로 우회하려면 결국 백엔드가 필요해 C와 같아진다.

### 6.2 권장안 A의 동작

```
config/keywords.json   ← 저장소에 커밋 (코드 아님, 설정 데이터)
{
  "keywords": ["시루풍력", "왕신풍력", "해파랑육상풍력"],
  "window_days": 90,
  "row_page": 100
}
```

- 대시보드 "정보공개 청구" 카드에 **"키워드 편집"** 버튼을 두고 GitHub 편집 URL로 연결한다.
  `https://github.com/jung372/BRE-Workflow-Automation2/edit/main/config/keywords.json`
- GitHub 로그인 계정으로 인증되므로 **별도 인증 구현이 불필요**하고, 토큰 노출도 없다. 모바일 브라우저에서도 편집 가능하다.
- **반영 시점: 다음 정시 실행(최대 1시간).** 재배포가 필요 없다.

**재배포 없이 반영되는 이유가 중요하다.** `keywords.json`을 `ci-deploy.yml`의 `paths-ignore`에 추가하고, 스크래퍼가 이 파일을 **`BRE_DATA_DIR`(= `publish` clone)** 에서 읽게 한다. `push_to_github.py`가 매 회차 스크래핑 **전에** `git pull --rebase`를 수행하므로, 원격에서 수정한 키워드가 자동으로 서버에 도달한다. 기존 배포 파이프라인을 그대로 재활용하는 셈이다.

로드 우선순위:

1. `BRE_DATA_DIR/config/keywords.json` — 서버 운영 경로
2. 저장소 루트 `config/keywords.json` — 개발 PC 폴백
3. 파일이 없거나 형식이 깨졌으면 **기본 키워드 3개로 동작하고 경고 로그**를 남긴다 (잘못된 편집으로 수집이 멈추지 않게)

### 6.3 접근 제어 — 추가 구현이 필요 없다

"권한 있는 사람만 키워드를 바꿀 수 있어야 한다"는 요구는 **GitHub 권한 모델이 이미 충족한다.** 저장소 실측(2026-08-06):

```
공개 여부   : PUBLIC
협업자      : jung372 (admin) — 1명
브랜치 보호 : 없음    룰셋 : 없음
```

- write 권한이 없는 사용자가 웹 편집기로 파일을 고치면 GitHub이 **자동으로 fork + PR로 전환**한다. 원본 저장소에 직접 커밋되지 않으며, 병합에는 소유자 승인이 필요하다.
- 따라서 `config/keywords.json`을 변경할 수 있는 사람은 현재 소유자 1명뿐이다. **추가 코드 0줄.**
- 변경 이력·변경자·시각은 git이 자동 기록한다. 별도 감사 로그가 필요 없다.

**브랜치 보호는 권하지 않는다.** 협업자가 1명이라 막을 대상이 없어 실익이 없고, `main`에 PR 필수를 걸면 **서버가 매시간 수행하는 데이터 push가 거부될 위험**이 있다. admin 우회가 기본으로 열려 있어 통과할 가능성이 높지만, 확실하지 않은 설정으로 운영 파이프라인을 건드리는 것은 이득 대비 위험이 크다. 같은 이유로 CODEOWNERS도 PR 필수 설정이 전제되므로 함께 무의미하다.

> **참고.** 저장소가 public이므로 `keywords.json`은 누구나 읽을 수 있다. 어떤 사업을 감시 중인지 드러나지만, 대시보드에 이미 사업명이 공개되어 있어 새로운 노출은 아니다. 감시 대상 자체를 비공개로 하려면 저장소 비공개화 + Pages 대체 수단이 필요해 별도 과제가 된다.

### 6.4 변경 안전성 — 실제로 막아야 할 것

침입보다 현실적인 위험은 **본인의 실수**다. 오타, JSON 문법 오류, 과도하게 광범위한 키워드(2.6항의 `시루` → 18,928건) 같은 것들이다.

| 방어 | 막는 것 | 추가 코드 |
|---|---|---|
| 런타임 폴백 + 경고 | 깨진 파일로 수집 중단 | ~10줄 (6.2항) |
| 스키마 검증 함수 | 형식 오류·개수 초과·짧은 키워드 | ~35줄 |
| 검증 단위 테스트 | 위 로직 회귀 | ~40줄 |
| 검증 전용 워크플로 | 잘못된 키워드가 운영에 도달 | ~25줄 YAML |
| 대시보드 칩 표시 | 변경 사실을 즉시 인지 | 5.1항에 포함 |

#### 검증 전용 워크플로가 필요한 이유

6.2항에서 `config/keywords.json`을 `paths-ignore`에 넣었다. 재배포 없이 반영되게 하려는 의도지만, **그 결과 키워드만 고친 push는 CI가 아예 실행되지 않는다.** 검증을 붙여도 돌지 않는다는 뜻이다.

그래서 `paths: ['config/keywords.json']`에만 반응하는 **검증 전용 워크플로**를 따로 둔다. 스키마만 확인하고 배포는 하지 않으므로 20초 내에 끝나고, 실패하면 GitHub에 실패 표시가 남는다.

대안으로 `paths-ignore`에서 제외해 전체 배포를 유발할 수도 있지만, 런타임이 어차피 `publish` clone에서 키워드를 읽으므로 **새 릴리스는 기능적으로 동일하다** — 의미 없는 5분짜리 재배포가 된다. 따라서 워크플로 분리를 택한다.

#### 검증 규칙 (잠정 — 확정 필요)

| 항목 | 규칙 | 위반 시 |
|---|---|---|
| `keywords` 타입 | 문자열 배열 | CI 실패 |
| 키워드 길이 | 3자 이상 | CI 실패 |
| 키워드 개수 | 1~20개 | CI 실패 |
| 중복 | 불허 | CI 실패 |
| `window_days` | 7~365 | CI 실패 |
| `row_page` | 10~200 | CI 실패 |
| 조회 건수 | 500건 초과 | 런타임 경고 (차단하지 않음) |

키워드 최소 길이 3자는 2.6항의 실측(`시루`·`왕신` 2자가 만 건 이상 오탐)에 근거한다. 이 값들은 확정 전 잠정치다.

### 6.5 선택안 C를 2단계로 남기는 이유

진짜 편집 UI(추가·삭제 버튼, 즉시 반영, 건수 미리보기)를 원한다면 서버 PC에 관리 페이지가 필요하다. 같은 서버에서 `Stock_Report_Codex`가 이미 Tailscale Serve로 사설 웹앱을 운영하고 있어 선례와 인프라가 있다. 다만 인증·CSRF·커밋 처리까지 필요해 비용이 크다.

**1단계(A)를 먼저 쓰고, 키워드 변경이 잦아 불편하다고 판단되면 C를 착수하는 것을 권한다.** A로도 "웹에서 수정"이라는 요구는 충족된다.

## 10. 열린 이슈

- **개별 공문 상세 링크.** `infoListDetl.do`/`infoListDetl2.do`/`infoListDetl3.do`가 존재하나 파라미터 형식을 확인하지 못했다. 1단계에서는 **키워드 검색 결과 URL**로 링크한다(항상 동작함). 상세 링크 형식을 확인하면 개별 문서로 연결하도록 개선한다.
- 원문정보 컬렉션 병행 조회 여부. 현 키워드로는 0건이지만 향후 사업이 진행되면 등장할 수 있다. 같은 세션에서 요청 1회만 추가되므로 저비용이다.
- 발송처별 필터·정렬 UI (건수가 늘어나면 검토)
- **6.4항 검증 규칙 확정** — 키워드 최소 3자·최대 20개 등이 잠정치다.
- **`BRE_SMOKE_MIN_OK` 재검토** — 사이트가 5→6개가 되므로 3을 유지할지 4로 올릴지 결정이 필요하다.
- 6.5항 방안 C(Tailscale 사설 관리 페이지) 착수 여부. 1단계 운영 후 판단.
